## Verdict: NOT-ADOPTED-justified (bordering NOT-APPLICABLE)

cqrs-htmx's own README states the gate: "**If you are not using go-cqrs-lite, this library is not for you** — it is the HTMX/HTTP binding for that specific CQRS core." The hub uses no cqrs-lite (see go-cqrs-lite.md, this group), has **no users, no sessions, no auth, and no write endpoints at all** — every route it serves is a GET (`hub/internal/cli/serve.go:83`, `hub/internal/dashboard/routes.go:58-60`; the only POST in the hub tree is the _outbound_ discovery client call, `hub/internal/discovery/client.go`). That empties the library's module families one by one: usermgmt + its three auth strategies solve a problem the bind posture deliberately excludes (localhost/unix-socket, single operator — `STACK.md:22`, `docs/decisions/bind-posture.md`); adminui administers usermgmt objects (users/tenants/members/audit) that do not exist here; dashboardui introspects event stores, journals, projections, DLQs and snapshots the hub does not have (its requires graph pulls `go-cqrs-lite/command`, `commandlifecycle`, `event`, `id` — `dashboardui/go.mod:11-15`); the root `App` handler pipeline (decode→Casbin authorize→validate→dispatch→HTMX response) has no dispatchers to bind and no HTMX to answer — the hub is DataStar by recorded decision (`STACK.md:46`). The two families with any surface-level overlap — SSE transport and the `datastar` adapter module — resolve against adoption: the hub already uses go-sse directly (the same wire-format layer cqrs-htmx's own SSE is built on), and the `datastar/v4` module's distinctive features (signal decoding for command POSTs, `EventBridge` mapping `go-cqrs-lite/event.Event` → patches) map to nothing the hub does while dragging `go-cqrs-lite/event/v4` + `id/v4` in as DIRECT requires (`datastar/go.mod:6-7`). This is the rare audit where the counterfactual inventory finds nothing the consumer lacks: the correct amount of cqrs-htmx for a userless, read-only, DataStar dashboard is zero.

**Flip trigger:** a posture change, not a library decision — if the hub ever serves _remote operators_ (multi-user access, sessions, login), usermgmt + loginpage + adminui become the fleet-standard path and this audit re-runs. Until the bind-posture decision itself changes (STACK.md:22 / `docs/decisions/bind-posture.md`), no feature growth inside the current posture (more views, more filters, more API routes) moves the needle, because none of it creates users or commands.

## Gap analysis

Nothing actionable. Every sub-module family was assessed against an actual hub need and none maps:

- **usermgmt/adminui/loginpage/setup** — the "hub administration" hypothesis fails concretely: what an operator administers here is _evidence windows, staleness thresholds, and the source_ — flags on `compliance-hub serve` (`hub/internal/cli/flags.go`), re-read by restarting the systemd unit. adminui's panels (accounts, tenants, members, audit log) have no data source to bind to without first adopting usermgmt, sessions, and a posture change.
- **dashboardui** — the second hypothesis ("observability dashboard for hub administration?") fails because dashboardui is CQRS-internal observability: it autodetects `EventSource`/`Journal`/`SeekableJournal`/`StreamReader`/`Host`/`DLQ`/`Snapshots`/`Bus` interfaces (`dashboardui/README.md` "Integration Modes") — interfaces only a go-cqrs-lite store can implement. The hub's SQLite cache implements none of them, and building adapters from `evidence_runs` to a journal-shaped interface would be pure ceremony.
- **SSE transport** — cqrs-htmx's `Broadcaster`/`SSEStream` and the hub's `events.Hub` are both thin layers over the same go-sse; the consumer already owns the richer one (typed snapshot/update/diff payloads + ring replay + DataStar projection). Swapping would lose `DiffRows` semantics and gain nothing.
- **datastar adapter** — the single module with a seductive name. Reality check line-by-line: `ScriptHandler()` ≙ already have (`routes.go:58`, version-pinned by go-datastar/static per `dashboard.go:112` comment); `ReadSignals` — the hub has zero POST routes; `NewResponse` builder — the hub's "patches-as-values" stance (STACK.md:46) is deliberately the opposite of a response-builder API; `EventBridge` — requires `go-cqrs-lite/event.Event`, i.e. the exact dependency this consumer's architecture excludes. And the module is on go-datastar v0.7.0 while the hub pins v0.6.x — adopting would fork the fleet's DataStar layer at two versions.

## Fleet leverage

cqrs-htmx is the fleet's multi-user GOTH-stack application framework (root + usermgmt + panels + setup; reference consumers are the example apps and the wider fleet's HTMX services). The two-way honesty: this is the most clear-cut of the three audits — there is no shared plumbing being duplicated here. The hub's realtime stack (go-sse + go-datastar + templ-components) is _already_ the same primitive layer cqrs-htmx itself builds on, so collective improvements flow between hub and framework consumers through those primitives regardless of adoption. The library's target shape — authenticated, command-dispatching, HTMX-rendered web app — is defined by exactly the properties the hub's design removes (users, commands, HTMX). The hub is not an under-served member of cqrs-htmx's audience; it is outside the audience, correctly. The only future convergence is the posture-change scenario in the flip trigger, which is a product decision about remote operators, not a library-utilization finding.
